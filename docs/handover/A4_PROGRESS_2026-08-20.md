## What this session changed

### 1. Resolved the eviction-race question with an observable + a bounded backstop (spec A4 §5)

The inherited `_make_session_room_locked` cancellation branch evicted the oldest
non-terminal session with `active_subscription == False`. That is the right
shape for a genuinely stuck session but has a real race: a fresh, legitimate
request inside its own submit→subscribe window has no subscription yet, so
oldest-first eviction could cancel it. This session:

- Added `created_at: float = field(default_factory=time.monotonic)` to `_Session`
  so every admitted session carries a monotonic admission timestamp.
- Added `ever_subscribed: bool = False` to `_Session`; flipped to `True` inside
  `RequestGatewayService.subscribe()` at the same point `active_subscription`
  is set.
- Added `RequestGatewayService.SESSION_EVICTION_GRACE_SECONDS = 0.05` as a
  bounded, frozen, exposed product constant. The new eviction path uses two
  rules:
    - **Fast path (observable, no timer).** A non-terminal session with
      `ever_subscribed == True` and `active_subscription == False` is
      observably abandoned — a consumer attached and vanished, so no
      further acks can ever arrive. Evict immediately. This is the
      correct treatment for the abandoned-tab case.
    - **Backstop path (timer, never-subscribed only).** A non-terminal
      session with `ever_subscribed == False` (i.e. the
      submit→subscribe window is still open, or the request is truly
      stuck from the first emission) is protected by the grace. The
      grace is a backstop, not the primary signal: a request that
      never subscribes can still pin capacity forever, so past the
      grace the eviction path fires.
- The backstop value `0.05` s is the same order of magnitude as the
  ordinary browser round-trip to the gateway observed in prior
  physical runs (1-50 ms per the previous session notes). The number
  is a heuristic; the observable fast path is what the eviction
  decision actually turns on for any session that ever subscribed.
  A future tightening would replace this backstop with an explicit
  "browser-handshake deadline" derived from a measured value, but
  doing that without empirical data would just rename the guess.
- Added two deterministic tests pinning the new contract:
  `test_ever_subscribed_then_vanished_is_evicted_immediately` (fast
  path; no grace) and
  `test_fresh_request_inside_subscribe_window_is_not_cancelled`
  (backstop path; rejected within the grace, not cancelled). The
  backstop is asserted to be `> 0` and `<= 0.5` so the property is
  exercised as a bounded product constant, not a hidden magic number.
  `test_stuck_session_evicted_after_grace_elapses` confirms the
  backstop does fire eventually.
- Updated the two inherited rewritten tests
  (`test_active_session_capacity_evicts_stuck_session_under_pressure`
  in `test_stream.py` and
  `test_session_capacity_evicts_oldest_unattached_under_pressure` in
  `test_lifecycle_public.py`) to assert the new grace-aware contract:
  a never-subscribed second submit is rejected inside the grace,
  then admitted after the grace. Re-adding `import time` in
  `test_lifecycle_public.py` (the prior diff had removed it).

This redesign is in response to the user feedback that the
`SESSION_EVICTION_GRACE_SECONDS = 0.05` constant "has no derivation
behind it" and that the correct shape is to track whether a session
has ever had a subscription, then evict it; the grace becomes a
backstop for the never-subscribed case.
